## 1. Executive Security & Integrity Assessment

The platform demonstrates high architectural security discipline compared to typical SME billing web apps:
- It uses **PostgreSQL Row-Level Security (RLS)** to enforce tenant boundaries at the database kernel level.
- It uses **hash-chained tamper-evident audit logs** for critical mutations.
- It validates double-entry ledger balance invariants ($\sum \text{Debit} = \sum \text{Credit}$).

However, this in-depth code audit has identified specific edge-case vulnerabilities, concurrency hazards, floating-point discrepancies, and security risks that must be hardened before wide-scale commercial rollout.

## 2. Critical Findings & Technical Vulnerabilities

### Finding 1: Potential Race Condition in Sequential Invoice Number Assignment
- **Severity:** `HIGH`
- **Category:** Concurrency / Data Integrity
- **File Path:** [`apps/api/src/invoices/invoices.service.ts`](file:///c:/Billing/my_bill_history/apps/api/src/invoices/invoices.service.ts)
- **Code Location:** `assignInvoiceNumber(companyId, financialYearId, tx)`
- **Vulnerability Description:**
  Invoice numbering fetches the current sequence number, increments it in JavaScript memory, and then updates the `invoice_sequences` table. If two cashiers at different billing counters click "Save & Print" simultaneously within the same millisecond, both transactions can read the same sequence value (e.g. `1042`), leading to a unique constraint collision (`duplicate key value violates unique constraint 'sales_invoices_company_id_invoice_number_key'`), causing one cashier's transaction to abruptly crash.
- **Impact:** Failed customer checkouts during peak rush hours at retail counters.
- **Evidence:**
  ```typescript
  const seq = await tx.invoiceSequence.findUnique({ where: { companyId_financialYearId: ... } });
  const nextVal = (seq?.currentValue || 0) + 1;
  await tx.invoiceSequence.upsert({ ... update: { currentValue: nextVal } });
  ```
- **Recommended Fix:**
  Use atomic database increment with row locking (`SELECT FOR UPDATE` or SQL atomic increment):
  ```typescript
  const updated = await tx.$queryRaw<{ current_val: number }[]>`
    UPDATE invoice_sequences
    SET current_value = current_value + 1
    WHERE company_id = ${companyId}::uuid AND financial_year_id = ${financialYearId}::uuid
    RETURNING current_value;
  `;
  ```

### Finding 2: Client-Side Floating Point Discrepancy on Invoice Line Totals
- **Severity:** `MEDIUM`
- **Category:** Calculation Correctness
- **File Path:** [`apps/web/src/app/sales/invoices/new/page.tsx`](file:///c:/Billing/my_bill_history/apps/web/src/app/sales/invoices/new/page.tsx)
- **Code Location:** `calculateTotals()`
- **Vulnerability Description:**
  In the browser form, tax line subtotals and discounts are calculated using native JavaScript IEEE 754 floating point arithmetic:
  `const tax = (rate * qty * (1 - discount/100)) * (taxRate / 100);`
  For quantities with 3 decimals (e.g., 2.375 kg @ ₹149.50/kg with 18% GST), floating point inaccuracies result in values like `64.08999999999999`. Meanwhile, the backend calculates using `Decimal.js` from `@billing/accounting-core`. In edge cases, the cashier sees ₹420.50 on the screen, but the final invoice generated by the backend totals ₹420.51.
- **Impact:** Cashier and customer confusion over $\pm ₹0.01$ differences on invoice summary.
- **Recommended Fix:**
  Export a shared lightweight calculation bundle from `@billing/accounting-core` and import it directly into `NewSalesInvoicePage` to ensure 100% mathematical identity between browser preview and backend commitment.

### Finding 3: Unhandled Reverse Charge Mechanism (RCM) Accounting Entries on Outward Invoices
- **Severity:** `MEDIUM`
- **Category:** Statutory Tax Accounting
- **File Path:** [`apps/api/src/invoices/invoices.service.ts`](file:///c:/Billing/my_bill_history/apps/api/src/invoices/invoices.service.ts)
- **Code Location:** `createSalesVoucher(invoice, tx)`
- **Vulnerability Description:**
  When `isReverseCharge` is set to `true` on a sales invoice (e.g., GTA transport services or scrap sales where the buyer pays tax directly to the government), the supplier does *not* collect GST. The backend correctly flags the invoice, but in the generated General Ledger voucher, the output tax is still credited to Output CGST/SGST liability accounts instead of passing through to an RCM informational tax ledger.
- **Impact:** Erroneous inflation of output GST liability on the company's Trial Balance for RCM supplies.
- **Recommended Fix:**
  In `createSalesVoucher`:
  ```typescript
  if (!invoice.isReverseCharge) {
    // Credit Output CGST & SGST Liability
    journalEntries.push(createTaxCredit(outputCgstAccount, invoice.cgstAmount));
    journalEntries.push(createTaxCredit(outputSgstAccount, invoice.sgstAmount));
  } else {
    // For RCM, total debtor amount equals taxable value only; tax is not collected
  }
  ```

### Finding 4: Missing Idempotency Validation on Duplicate Bill Submission
- **Severity:** `MEDIUM`
- **Category:** Operational Integrity
- **File Path:** [`apps/api/src/invoices/invoices.controller.ts`](file:///c:/Billing/my_bill_history/apps/api/src/invoices/invoices.controller.ts)
- **Code Location:** `@Post() async createInvoice(...)`
- **Vulnerability Description:**
  Although `apiClient` supports passing an `idempotency-key` header, the backend `InvoicesController` does not validate this key against a Redis cache or database store. If a network latency spike causes the cashier to double-click "Submit", two identical sales invoices with consecutive invoice numbers and duplicate stock reductions will be created.
- **Impact:** Duplicate billing, erroneous customer debt, and corrupted physical stock count.
- **Recommended Fix:**
  Implement a NestJS `IdempotencyInterceptor` backed by Redis `SET key val NX EX 60` to reject duplicate submissions within a 60-second window.

### Finding 5: Image Upload File Size & MIME Verification in Bill Scanner
- **Severity:** `LOW`
- **Category:** API Security / Resource Exhaustion
- **File Path:** [`apps/api/src/purchases/purchases.controller.ts`](file:///c:/Billing/my_bill_history/apps/api/src/purchases/purchases.controller.ts)
- **Code Location:** `@Post('scan-bill')`
- **Vulnerability Description:**
  The Fastify multipart handler accepts file streams for OCR parsing. While it filters by `.pdf`, `.png`, and `.jpg` extensions, it does not inspect magic bytes to verify genuine image headers or enforce strict memory caps before feeding the stream into `tesseract.js` worker threads. A corrupted or oversized 50MB file could cause CPU exhaustion on a lightweight VPS.
- **Impact:** Denial of Service (DoS) of OCR processing queue.
- **Recommended Fix:**
  Enforce a strict 10MB limit in Fastify multipart config and validate file buffer headers (`image/jpeg`, `image/png`, `application/pdf`) prior to invoking OCR workers.

### Finding 6: Demo User Helper Display in Production
- **Severity:** `LOW`
- **Category:** Information Exposure
- **File Path:** [`apps/web/src/app/login/page.tsx`](file:///c:/Billing/my_bill_history/apps/web/src/app/login/page.tsx#L153)
- **Code Location:** `handleDemoCredentials`
- **Vulnerability Description:**
  The login page conditionally renders the demo button based on:
  `(process.env.NODE_ENV !== "production" || process.env.NEXT_PUBLIC_ENABLE_DEMO_CREDENTIALS === "true")`
  If a production deployment inadvertently includes `NEXT_PUBLIC_ENABLE_DEMO_CREDENTIALS="true"` in the environment variables, the demo login button will appear publicly on the internet.
- **Impact:** Unauthorized public access if demo credentials remain seeded in production.
- **Recommended Fix:**
  Add a compile-time check or strip the demo block completely in production Next.js builds unless explicitly running on a staging domain.
